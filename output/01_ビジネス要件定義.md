## 4. 現状課題（Before）と10年後（After）

| 観点 | Before（今） | After（10年後／このプロダクト） |
|---|---|---|
| **登録** | 品名・型番・場所を目で確認し、メモしてからExcelに入力する。**入力が面倒で後回し**になる | 映して話すだけ。AIが品名・メーカー・型番を読み取り、場所などは音声で補う |
| **識別（シール/QR/NFC）** | シール・タグの**貼付と発行が手間**。剥がれ・汚れ・貼り忘れがある。**タグの無い物は管理できない**。大型機械や屋外設備には貼りにくい | **物そのものの見た目**で識別する。タグが無くても登録・照合できる |
| **棚卸** | 台帳を印刷し、1点ずつ現物と照合する。年1回・数日がかり | ロボットやカメラの巡回で**いつでも棚卸**できる（将来構想） |
| **移動** | 会議室や工場間で移動しても申請されず、**所在不明**になる | 映った場所で所在を自動更新する（将来構想） |
| **除却** | 廃棄しても台帳に残る（**幽霊資産**）。固定資産税や減価償却の計算が過大になる | 「見つからない資産」をAIが知らせ、除却の候補を出す（将来構想） |
| **担当者** | 総務・経理の兼務者が1人で抱え、**属人化**している | AI社員が下書きを作り、人は確認・承認するだけ |
| **中小企業** | **規模が小さいほど管理が形だけになる**。専用システムは高く、設定も面倒 | スマホとスプレッドシートだけで始められ、導入のハードルが低い |

**解決する課題（今回）**: 「台帳を作る・登録する」最初の段階が大変で、ここが回らないと棚卸・移動・除却も回らない（`input/02` の議論の結論）。

## 5. 今回フォーカスする業務と機能

**業務**: 固定資産の**新規登録（台帳の作成）**に絞る。

| 区分 | 内容 |
|---|---|
| **範囲内（作る）** | ・Webアプリでカメラを起動し、**動画＋音声**で固定資産を1件ずつ登録<br>・AIが映像から品名・カテゴリなどを推定し、音声から場所などを抜き出す<br>・スプレッドシート（台帳）へ1行追加する<br>・登録された台帳を画面で確認する |
| **範囲外（今回は作らず、将来構想として見せる）** | ・ロボットの巡回による自動登録・自動更新<br>・メガネ型デバイス（AIグラス）・常時カメラ<br>・棚卸照合、移動、除却の処理<br>・チャットで台帳を検索する機能（`input/03` のMVP3。今回はMVPに入れない）<br>・購入の代行（Amazon等）、会議室準備の依頼<br>・会計システム連携・減価償却の計算<br>・ログイン・権限管理・複数拠点への対応 |
| **やらないと決めたこと** | **写真のアップロードとキーボード入力はしない**（`input/04`。`input/03` の「写真から認識」案より04を優先） |

## 6. デモの機能要件

### 6.0 最重要要件

> **R-0（MUST）: 登録の操作は「動画＋音声」だけで完結すること。写真のアップロードやテキスト入力は求めない。**
> 画面のタップは、撮影の開始・停止など最小限だけにする（仮定）。

### 6.1 デモの流れ（1本道のユーザーストーリー）

| Step | ユーザー（佐藤さん） | システム（AI） | 担当 |
|---|---|---|---|
| 1 | 登録画面を開き、「撮影開始」をタップする | カメラとマイクを起動し、録画を始める | C |
| 2 | 会議室のモニター（例）を映しながら「これは第1会議室のモニター。去年の4月に15万円くらいで買いました」と話す | 動画と音声を受け取る | C |
| 3 | 「撮影終了」をタップする（または「登録して」と話す＝SHOULD） | 映像から品名・カテゴリ・メーカー・型番を推定し、音声を書き起こして場所・取得日・価額を抜き出す | B |
| 4 | 認識結果を画面で見る | 読み取った項目と、画像（フレーム）を表示する | C |
| 5 | （足りない項目があれば）AIが音声で質問し、ユーザーが声で答える＝SHOULD | 項目を補う | B/C |
| 6 | 内容を確認し、登録を確定する | スプレッドシートに1行追加し、資産番号を振る | B |
| 7 | 台帳確認画面を開く | 登録された行が一覧に表示される | C |

**デモの見せ場**: キーボードに一切触らずに、映して話しただけで台帳に1行増える。できれば事務所の物と工場っぽい物の2件を登録する（仮定）。

| F1-5 | 抜き出した結果を画面に表示する（どの項目を読み取れたか分かるように） | MUST |
| F1-6 | 登録を確定すると、スプレッドシートに1行追加される | MUST |
| F1-7 | 処理中の表示（「AIが確認中…」など）を出し、デモが止まって見えないようにする | MUST |

| ID | 要件 | 優先度 |
|---|---|---|

| F2-3 | 登録時の画像（フレーム）のサムネイルを表示する | SHOULD |
| F2-4 | 行を選ぶと詳細（全項目・音声の書き起こし）を表示する | SHOULD |

### 6.4 裏側（データ・AI）

| ID | 要件 | 優先度 |
|---|---|---|
| B-1 | **スプレッドシート（Google Sheets を想定）をDBとして使う**。1資産＝1行 | MUST |
| B-2 | AIの出力は、台帳の列に合わせた**JSON**で返す（列の設計はB/Cが決める） | MUST |
| B-3 | 資産番号・登録日時・登録方法は、システムが自動で付ける | MUST |
| B-4 | 読み取れなかった項目は空欄のまま登録する（エラーで止めない） | MUST |
| B-5 | 画像（フレーム）を保存し、参照URLを台帳に書く | SHOULD |
| B-6 | 各項目がどこから入ったか（映像／音声）と、AIの確信度を記録する | SHOULD |

### 6.5 デモを安定させるための要件

| ID | 要件 | 優先度 |
|---|---|---|

| D-2 | 本番でAIやネットワークが失敗したときの予備（事前に撮った動画、または登録済みの行）を用意する | MUST |
| D-3 | 審査員が触って試せるURL、または動かし方の手順を用意する（提出フォームで必要） | MUST |

## 7. 審査5観点への対応

| 観点 | 何で点を取るか |
|---|---|
| **価値**（誰の役に立つか） | 総務・経理を兼務する中小メーカーの担当者（ペルソナの佐藤さん）が、面倒で後回しになっていた台帳登録を「映して話すだけ」で終えられる。形だけになりがちな中小企業の固定資産管理を立て直す |
| **実現性**（動くか・使えるか） | デモの1本道（撮影 → 認識 → 登録 → 確認）を**実機のライブで**見せる。仕組みはWebアプリ＋スプレッドシートと単純で、明日から試せる。予備の動画も用意する |
| **新規性** | シール・QR・NFCに頼らず、**物そのものを見て識別する**。キーボードも写真アップロードも使わず、「動画＋音声だけ」で入力する |
| **AIの活かし方** | 映像の理解（品名・銘板の読み取り）と、音声の理解（場所・価額の抜き出し）をAIが組み合わせ、台帳の列へ構造化する。人は確認するだけ（AI社員の働き方） |
| **展開性** | 入力はそのままに、スマホ → AIグラス → 巡回ロボットへ置き換えられる。登録 → 棚卸 → 移動 → 除却へ機能を広げ、製造業以外（オフィス・病院・学校・農業）にも使える（第8章） |

同点時の判定（「動くか」→「誰の役に立つか」）に備え、**デモを確実に通すことと、ペルソナの具体性**を最優先にする。

**発表での締め方**: 「今日はスマホで人が歩いて映しましたが、10年後はロボットが勝手に歩いて映します。台帳の仕組みは、今日作ったものと同じです。」
